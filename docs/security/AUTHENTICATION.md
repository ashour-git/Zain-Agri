# ZAIN AGRI — Authentication

Status: Sprint 02
Last updated: 2026-10-31

This document describes how a person proves who they are, how the resulting
session is carried, and how it is destroyed. Authorisation is a separate
concern — see `RBAC.md` and `TENANT_ISOLATION.md`.

---

## 1. Design at a glance

| Concern | Decision |
|---|---|
| Password storage | Argon2id (`argon2-cffi`), per-password salt, tuned cost |
| Access credential | JWT, HS256, 15 minutes, sent as `Authorization: Bearer` |
| Refresh credential | Opaque 48-byte token, cookie-only, 30 days |
| Refresh storage | SHA-256 hex digest only; the raw token is never persisted |
| Rotation | Every refresh revokes its predecessor and issues a successor |
| Reuse detection | Replaying a rotated token revokes the entire token family |
| Revocation | Session row check on every request (`sid` claim → `refresh_sessions`) |
| Client storage | Access token in memory; refresh token in an HttpOnly cookie |
| CSRF | `SameSite=Lax` + explicit `Origin`/`Referer` validation |
| Rate limiting | In-process sliding window on login/register/refresh |

The access token is deliberately **not** a standalone proof of identity. It is a
short-lived pointer to a database session that is re-validated on every request,
which is what makes "revoke this device now" actually work in a point-of-sale
system.

## 2. Token model

### 2.1 Access token

```
HS256(
  sub = user id            # who
  sid = refresh session id # which device/session
  tid = tenant id | null   # advisory; never trusted for authorisation
  rol = role | null        # advisory; never trusted for authorisation
  jti = random id
  typ = "access"
  iat, exp                 # exp = iat + ACCESS_TOKEN_TTL_MINUTES (15)
  iss = "zain-agri"
  aud = "zain-agri-api"
)
```

Validation checks signature, `exp`, `iss`, `aud`, and `typ == "access"`. A token
with `typ = "refresh"`, a foreign signature, or an expired timestamp is rejected
with `401`.

`tid` and `rol` exist so the UI can render without an extra round trip. They are
**advisory only**: `get_current_tenant` re-reads the membership and tenant status
from the database, so demotions, suspensions and deletions take effect on the
next request, not on the next token refresh.

### 2.2 Refresh token

- Generated by `secrets.token_urlsafe(48)` — 384 bits of entropy.
- Stored as `sha256(token).hexdigest()` in `refresh_sessions.token_hash`.
- Delivered in `Set-Cookie: zain_refresh=…` with:

| Attribute | Value |
|---|---|
| `HttpOnly` | always |
| `Secure` | `REFRESH_COOKIE_SECURE` (must be `true` in production) |
| `SameSite` | `Lax` |
| `Path` | `/api/v1/auth` |
| `Max-Age` | `REFRESH_TOKEN_TTL_DAYS × 86400` |

The `Path` scope means the browser does not attach the cookie to product
endpoints at all; those are authenticated by the bearer token.

### 2.3 Token families

A login creates a new `token_family_id`. Each rotation inserts a new row in the
same family and sets `revoked_at` + `replaced_by_id` on the old one.

If a request presents a token whose row is already revoked, the API assumes the
token was stolen and revokes every still-active row in that family before
returning `401`. Both the attacker and the legitimate device are logged out,
which is the correct trade-off: a detected theft is not recoverable by guessing
which branch is genuine.

Concurrent refreshes are serialised with `SELECT … FOR UPDATE` on the token row,
so two tabs cannot both rotate the same token into two live branches.

## 3. Endpoints

All paths are under `/api/v1`.

| Method | Path | Auth | Success | Notes |
|---|---|---|---|---|
| `POST` | `/auth/register` | none | `201` | Creates the user, issues a session with no workspace |
| `POST` | `/auth/login` | none | `200` | Optional `tenant_id` selects a workspace |
| `POST` | `/auth/refresh` | cookie | `200` | Rotates; optional `tenant_id` switches workspace |
| `POST` | `/auth/logout` | cookie | `204` | Idempotent; clears the cookie |
| `POST` | `/auth/logout-all` | bearer | `204` | Revokes every live session for the user |
| `GET` | `/auth/me` | bearer | `200` | Identity, current workspace, available workspaces |
| `GET` | `/auth/sessions` | bearer | `200` | Live sessions, current one flagged |
| `DELETE` | `/auth/sessions/{id}` | bearer | `204` | Revokes one session; `404` if not yours |

Successful register/login/refresh responses contain the access token, never the
refresh token:

```json
{
  "access_token": "eyJ…",
  "token_type": "bearer",
  "expires_in": 900,
  "user": { "id": "…", "email": "…", "full_name": "…", "is_active": true },
  "tenant": { "id": "…", "name": "…", "slug": "…", "status": "active" },
  "role": "owner",
  "permissions": ["tenant.settings.manage", "…"],
  "tenants": [{ "id": "…", "name": "…", "role": "owner", "status": "active" }],
  "requires_tenant_selection": false
}
```

`requires_tenant_selection` is `true` when the user has no active membership, or
has more than one and did not name one. The web client then routes to
`/select-tenant` instead of the dashboard.

### 3.1 Login and tenant selection

1. Look up the user by normalised email.
2. Verify the Argon2id hash. An unknown email still performs a dummy hash
   verification, so response time does not reveal whether the account exists.
3. Reject inactive accounts with the same `401 Invalid email or password`.
4. Resolve the workspace:
   - `tenant_id` supplied → must be an active membership in an active tenant,
     otherwise `403 You do not have access to this workspace`.
   - exactly one active membership → bind it.
   - zero or several → leave the session unbound (`tenant_id = null`).

The login response never states whether the email exists, whether the password
was wrong, or whether the account is disabled.

### 3.2 Register and onboarding

Registration creates the user and a session with `tenant_id = null`. The user
then calls `POST /api/v1/tenants` with a name; that transaction creates the
tenant, the `OWNER` membership, and rotates the session so it is bound to the
new workspace. See `AUTHENTICATION.md` §5 and `TENANT_ISOLATION.md`.

There is no endpoint that joins an existing workspace by id. A client can only
create a workspace it will own.

## 4. Session lifecycle

```
register ──► [session A: no tenant] ──create workspace──► [session B: tenant]
login    ──► [session C: tenant?]
refresh  ──► revoke C, issue D (same family)
logout   ──► revoke current, clear cookie
logout-all / DELETE /sessions/{id} ──► revoke now, access token dies immediately
membership suspended / tenant suspended / user disabled
         ──► next request rejected (401/403) and refresh refused
tenant deleted
         ──► refresh_sessions row cascades away; access token 401s
```

`GET /auth/sessions` returns only non-revoked, non-expired rows owned by the
caller. Token hashes and family ids are not part of the contract.

## 5. Rate limiting

`app/core/ratelimit.py` implements a process-local sliding window keyed by
`(scope, client ip, email)`. Defaults: 10 attempts per 300 seconds for login,
register and refresh. Exceeding it returns `429` with `Retry-After`.

**Limitation:** the counter is per worker. With N uvicorn workers the effective
limit is N × configured value, and a restart clears it. A shared store (Redis)
is a production follow-up, listed in §9.

## 6. CSRF

The refresh cookie is the only ambient credential, so it is the only CSRF
surface. Two controls apply to unsafe methods (`POST`, `PATCH`, `PUT`, `DELETE`)
that carry the cookie:

1. `SameSite=Lax` prevents the cookie from being sent on cross-site POSTs in
   modern browsers.
2. `OriginGuardMiddleware` requires an `Origin` (or a `Referer` whose origin
   matches) drawn from `CORS_ORIGINS`. A request without one is rejected with
   `403 csrf_rejected`.

Bearer-authenticated requests are unaffected: an attacker's page cannot read or
set the in-memory access token, so requiring an `Origin` there would only break
non-browser clients.

If the guard is disabled because `CORS_ORIGINS` is empty, the API logs
`auth.csrf_disabled` at `WARNING`. Production configuration refuses to start
without explicit origins.

## 7. Account activation and email verification

`users.is_active` is checked at login, at refresh, and on every authenticated
request. `users.email_verified_at` exists for the future verification flow.

`REQUIRE_EMAIL_VERIFICATION` defaults to `false` because no mail transport is
configured. When enabled in production:

1. Registration sets `email_verified_at = null` and does **not** issue a usable
   session.
2. A signed, single-use token is emailed.
3. `POST /auth/verify-email` sets the timestamp.

No development-only verification shortcut is implemented. Adding one is
forbidden in production; if it is ever needed, it must be gated on
`ENVIRONMENT == "development"` and refuse to mount otherwise.

## 8. Configuration

| Variable | Default | Production requirement |
|---|---|---|
| `JWT_SECRET_KEY` | dev placeholder | ≥ 32 random characters, secret manager |
| `ACCESS_TOKEN_TTL_MINUTES` | `15` | keep short |
| `REFRESH_TOKEN_TTL_DAYS` | `30` | business decision |
| `REFRESH_COOKIE_SECURE` | `false` | **must be `true`** |
| `REFRESH_COOKIE_NAME` | `zain_refresh` | — |
| `CORS_ORIGINS` | empty | explicit HTTPS origin(s), no wildcards |
| `REQUIRE_EMAIL_VERIFICATION` | `false` | `true` once mail is configured |
| `AUTH_RATE_LIMIT_ATTEMPTS` | `10` | tune to traffic |
| `AUTH_RATE_LIMIT_WINDOW_SECONDS` | `300` | — |
| `ARGON2_TIME_COST` / `MEMORY_COST` / `PARALLELISM` | `3` / `65536` / `4` | benchmark on target hardware |

`Settings._validate_security_posture` refuses to start in production when the
JWT secret is the development default or shorter than 32 characters, when the
refresh cookie is not `Secure`, or when `CORS_ORIGINS` is empty.

## 9. Threat model

| Threat | Control | Residual risk |
|---|---|---|
| Password database theft | Argon2id, per-password salt, tuned memory cost | Offline cracking if the cost is too low for the hardware; benchmark at deploy |
| Credential stuffing | Generic errors + per-IP/email throttle | Per-worker limiter; add a shared store and account lockout policy |
| XSS stealing tokens | Refresh token HttpOnly; access token in memory, never localStorage | XSS can still act as the user while the page is open; CSP is not configured yet |
| Token replay after rotation | Reuse detection revokes the family | A stolen token used before the legitimate refresh goes unnoticed |
| Stolen access token | 15-minute TTL + session row check on every request | The thief has up to 15 minutes unless the session is revoked |
| CSRF | SameSite=Lax + origin guard | Old browsers ignoring SameSite; the origin guard covers them |
| Session fixation | Server generates all token ids; rotation on login and onboarding | — |
| Enumeration | Uniform `401` for unknown email, wrong password, inactive account | Timing differences are minimised but not formally measured |
| Cross-tenant token reuse | `tid` is advisory; membership re-read from the database | A token for tenant A cannot be edited into tenant B without the signing key |
| Log leakage | Logs contain event names, user/tenant ids, never passwords or tokens | Request bodies are not logged by design |

## 10. Known limitations

1. **Access tokens are checked against the database on every request** (one
   primary-key lookup on `refresh_sessions`). This is intentional — it is what
   makes revocation immediate — but it means the JWT saves no database work.
   If the lookup ever becomes a bottleneck, a short-lived in-process cache with
   a hard TTL can be added without weakening the model.
2. **Rate limiting is per process** (§5).
3. **No email delivery**, so verification is modelled but not enforced (§7).
4. **No password reset flow.** It needs mail transport and a single-use token
   table; it is not part of Sprint 02.
5. **No MFA.** A future `user_mfa` table and a challenge step in login.
6. **No device fingerprinting or "remember this device"** beyond the user agent
   string shown in the session list.
7. **Refresh token cleanup.** Expired rows are ignored at read time but not
   deleted. A scheduled `DELETE … WHERE expires_at < now() - interval '30 days'`
   is required before the table grows unbounded.
